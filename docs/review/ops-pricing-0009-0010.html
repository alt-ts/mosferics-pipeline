The ops and pricing schemas, as Postgres now holds them

Ten tables and one view, closing Stage 4's schema work. The cycle turned on a single question — whether a stored margin_pct breaks hard rule 7 — and the answer reshaped both the migration and the rule.

Live and scratch are both at 0010. Every table is empty except ops.channels (the Trade store) and ops.delivery_config (Tue/Wed/Thu, 12:00 Europe/London, one handling day). Remaining in Stage 4: stock if it is wanted before the pilot, and the role grants below.

Two margins, not one

Hard rule 7 says the gross margin is derived at query time and never stored. The data model specifies a stored margin_pct on variant_prices. Both documents were right and neither said which margin it meant.

the live margin

final_price against today’s cost

This is the one rule 7 is about. A stored copy goes stale the moment cost moves and then lies about the current relationship between price and cost — which is the failure the rule exists to prevent. It now has a name of its own: pricing.live_margins.

the snapshot

The margin the approval gate judged

margin_pct records the margin at the moment the price was calculated. It is a stored output, not the stored input rule 7 forbids — nobody types a margin and has the system back-solve a price from it.

The snapshot is kept because it cannot be rebuilt. cost_basis holds a current cost with no history, so once cost moves, the calc-time cost is gone and margin_pct is the only record of what the gate actually saw. From the scratch test, both figures for one variant:

variantfinal_pricecost now gross_marginmargin_pct_at_calcstatus
healthy40.00 28.000030.000 30.000auto_approved
lossmaker55.00 33.600038.909 −8.500approved

The second row is the whole argument: a price flagged as a loss-maker when it was set, healthy against today’s lower cost. Drop the column and that story is unrecoverable.

left join

An uncosted variant must not vanish

The view joins cost_basis with a LEFT JOIN. A variant priced with no cost row has an unknown margin, and NULL says so; an inner join would drop the row instead, so a count of the view would agree with nothing and quietly hide the gap. The test asserts the view and the price table return the same number of rows.

nullif

A free line does not divide by zero

final_price = 0 is legal — the CHECK bars negatives, not zero — and a zero denominator would take the whole query down. NULLIF(final_price, 0) returns NULL for that row and leaves the rest of the result intact.

column comment

The snapshot says what it is, in psql

COMMENT ON COLUMN puts the warning where \d+ shows it, so the distinction survives the moment everyone has forgotten this conversation. The name margin_pct_at_calc was offered and turned down as unnecessary once the comment and the view exist.

Judgement calls in ops

cardinality

A delivery config with no delivery days

The first version of this constraint read array_length(delivery_days, 1) > 0 and let an empty array straight through: array_length returns NULL rather than 0 for an empty array, and a CHECK passes on NULL. It was caught on scratch only because the test showed a ROLLBACK with no ERROR beside it. cardinality() returns 0 and the constraint bites.

single row

A config table that cannot grow a second row

CHECK (config_id = 1) makes delivery_config a one-row table by construction. The alternative — a table with an active flag — invites two active rows and a question about which one the promise engine read. There is only ever one delivery promise, so the schema says so.

containment

Weekday names without an enum type

delivery_days <@ ARRAY['mon', …] pins the values with a containment test rather than a Postgres enum. An enum would need its own migration to change and orders its values implicitly; the array is checked just as strictly and stays ordinary text the pipeline can compare without a cast.

biconditional

A finished run cannot still say running

(status = 'running') = (finished_at IS NULL) is an equality between two booleans, not an implication, so it catches both halves: a run marked succeeded with no finish time, and a run still marked running that has one. One constraint, both mistakes.

three constraints

The review queue is honest in both directions

closed_has_resolver, open_is_unresolved and resolution_complete look like one rule written three times. They are not: the first stops a resolved row with nobody's name on it, the second stops an open row that already carries a resolver, and the third keeps the who and the when together. Each names a different mistake, so each gives a different error.

for link.py

Orphaned preferred links must surface here

Carried forward from 0007 and not yet built: a confirmed variant with zero preferred links is a real gap — the demote trigger can clear the flag without anything raising — and ops.review_queue is where it has to appear, under entity_type = 'variant_link'. The table now exists to receive it; the query that finds them is a Stage 7 job.

Judgement calls in pricing

build order

ops moved ahead of pricing to get a real FK

The build doc had pricing at 0009 and ops at 0010, which would have left variant_prices.channel_id pointing at a table that did not exist. The choice was a deferred constraint or a swap. Nothing in ops depends on pricing, so the swap cost nothing and the foreign key is real from the first day.

two directions

vat_rate is pinned by the type and the CHECK

numeric(5,4) caps at 9.9999, so a bare 20 for 20% is rejected by the type — the classic 0.20-versus-20 slip. The CHECK then earns its keep on what the type still allows: negatives, and the 1–10 band where a stray 5.0 would mean 500%. Overlapping at the top end, not redundant.

asymmetric

margin_pct is bounded above but not below

Gross margin cannot reach 100% — that would need zero cost — so the upper bound is a real fact about the arithmetic. There is deliberately no lower bound: a price below cost gives a negative margin, and that is precisely the case the 15% floor exists to catch. Constraining it away would hide the thing the gate is for.

one constraint

Each pricing method carries its own range

ck_rules_value_matches_method is a single disjunction covering all three methods, because the legal range for value depends on which method names it: a markup is any non-negative number, a fixed margin must sit under 100, a target price must be positive. Three constraints would have let a row satisfy the wrong one.

Found while checking the view: nothing has any grants

blocks stage 5

No role can read anything, in any schema

Checked on live at 0010: relacl is empty on every table in every schema and pg_default_acl has no rows at all. The Stage 2 grant block was deferred to Stage 4 and never run. It has gone unnoticed because everything so far connects as mos_owner; NocoDB is what breaks first, connecting as mos_nocodb and showing an empty database.

doc corrected

FOR ROLE mos_owner is not optional

Default privileges attach to the role that will create the object, defaulting to whoever runs the statement. The doc said to run the block as postgres, which would have recorded postgres — while Alembic creates as mos_owner. Every later migration’s tables would still be born ungranted, and the statement guarding against exactly that would have been the thing that failed.

verified

Views need no separate grant

ALL TABLES IN SCHEMA covers views: on scratch, live_margins picked up mos_pipeline=r alongside the three real tables. Worth knowing because a view runs with its owner’s rights — so the margin can be granted to someone who is not granted the cost table underneath it.

--
-- Name: live_margins; Type: VIEW; Schema: pricing; Owner: mos_owner
--

CREATE VIEW pricing.live_margins AS
 SELECT vp.variant_id,
    vp.channel_id,
    vp.final_price,
    cb.cost_per_base_unit,
    round((((vp.final_price - cb.cost_per_base_unit) / NULLIF(vp.final_price, (0)::numeric)) * (100)::numeric), 3) AS gross_margin,
    vp.margin_pct AS margin_pct_at_calc,
    vp.status,
    cb.computed_at AS cost_computed_at
   FROM (pricing.variant_prices vp
     LEFT JOIN pricing.cost_basis cb ON ((cb.variant_id = vp.variant_id)));
