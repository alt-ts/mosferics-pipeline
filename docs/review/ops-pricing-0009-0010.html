Migrations 0009–0013 · all applied to live 17 Aug 2026

The ops and pricing schemas, as Postgres now holds them

Ten tables and one view, closing Stage 4’s schema work. The view shipped with a margin bug that flattered every multi-unit line, and fixing it turned up a second, quieter problem: no role in the database had ever been granted anything.

Live and scratch are both at 0013. Every table is empty except ops.channels (the Trade store) and ops.delivery_config (Tue/Wed/Thu, 12:00 Europe/London, one handling day). Remaining in Stage 4: stock, if it is wanted before the pilot.

The margin was wrong, and wrong in the flattering direction

The view shipped at 0010 computed (final_price − cost_per_base_unit) / final_price. But the cost is the cost of one base unit while the price is the price of the whole variant — and we sell in boxes. The missing term is × base_units_per_variant.

variantpack factorcost/unit variant costsell0010 said truth
single1 2.002.00 18.0088.889 88.889
box of 66 2.0012.00 18.0088.889 33.333
case of 2424 2.0048.00 18.0088.889 −166.667

Three properties made this dangerous. The error always overstates margin, so a thin line looks comfortable. It scales with pack size, so the worst cases are the worst affected — the bottom row is a line losing 167% that the view called healthy. And it disappears entirely at a pack factor of 1, which is why the 0010 test passed: it used a single implied unit and got the right answer for the wrong reason.

no default of 1

A missing pack factor reports nothing

base_units_per_variant is nullable, so a variant nobody has populated now returns a NULL margin where it previously returned a confident wrong one. Coalescing it to 1 was rejected: that reproduces this exact bug for precisely the rows nobody has checked, and does it silently.

traceable

A NULL says which input is missing

base_units_per_variant and the derived variant_cost are now columns of the view, so an empty margin can be read straight back to its cause — no cost row, or no pack factor — without a second query against two more tables.

inner join

Reaching for the pack factor drops no rows

The join to catalog.variants is an inner join, unlike the one to cost_basis. It cannot lose a row: variant_prices.variant_id is NOT NULL and carries a foreign key, so every price row has exactly one variant. The 0010 invariant — view rows equal price rows — still holds and is still asserted.

Two margins, not one

Hard rule 7 says the gross margin is derived at query time and never stored. The data model specifies a stored margin_pct. Both were right and neither said which margin it meant.

the live margin

final_price against today’s cost

The one rule 7 is about. A stored copy goes stale the moment cost moves and then lies about the current relationship between price and cost. It now has a name of its own: pricing.live_margins.

the snapshot

The margin the approval gate judged

margin_pct records the margin at the moment the price was calculated. A stored output, not the stored input rule 7 forbids — nobody types a margin and has the system back-solve a price from it.

The snapshot is kept because it cannot be rebuilt: cost_basis holds a current cost with no history, so once cost moves, the calc-time cost is gone and margin_pct is the only record of what the gate saw. A snapshot of −8.500 beside a live 38.909 is a real audit story — flagged as a loss-maker when set, healthy against today’s lower cost. The view returns both side by side, so that comparison is one read.

Nothing in the database had any grants

Found while checking that the margin view would be readable. relacl was empty on every table in every schema and pg_default_acl had no rows at all — the Stage 2 block was deferred to Stage 4 and never run. Nothing had noticed because everything so far connects as mos_owner; NocoDB would have been the first thing to open onto an apparently empty database.

now a migration

GRANT is DDL, and rule 5 has no carve-out

The build doc had this as a psql snippet run by hand. It is now migration 0013, for three reasons: hard rule 5 forbids ad-hoc DDL; Stage 4’s own exit criterion says upgrade head builds the database from empty, which was not meaningfully true while the result worked for mos_owner alone; and a migration can be tested on scratch, which a hand-run snippet never is.

the silent trap

FOR ROLE mos_owner is what makes it work

Default privileges attach to the role that will create the object, defaulting to whoever runs the statement. As written, run as postgres, it would have recorded postgres — while Alembic creates as mos_owner. Every later table would still be born ungranted, and the statement guarding against that would be the thing that failed. 0013 tests it with a probe table.

raw stays raw

No role holds UPDATE on import_rows

The blanket grant on raw is SELECT and INSERT only, with UPDATE (status) added back on import_batches by name. The audit trail is already immutable by trigger from 0004; withholding the privilege makes the permission system say the same thing, so hard rule 11 survives someone dropping the trigger.

found in passing

Without this grant, no SKU is ever allocated

catalog.mosferics_sku_seq is the one sequence not owned by an identity column, and next_mosferics_sku() calls nextval as the caller, not as definer. Identity columns need no sequence grant, so this one is easy to miss — and it would have failed on the first import and nowhere earlier.

column-level

The reviewer’s price rights are three columns wide

mos_nocodb holds UPDATE on override_price, status and approved_by — not the row. The Stage 0 register locks their price rights to the override, so the database says so rather than trusting the UI not to offer calculated_price.

when stock lands

A new schema inherits nothing

Default privileges are per-schema, so stock will arrive ungranted no matter what 0013 did. It has to be added to DATA_SCHEMAS and granted in the same migration that creates it.

Judgement calls in ops

cardinality

A delivery config with no delivery days

The first version read array_length(delivery_days, 1) > 0 and let an empty array straight through: array_length returns NULL rather than 0 for an empty array, and a CHECK passes on NULL. Caught on scratch only because the test showed a ROLLBACK with no ERROR beside it.

single row

A config table that cannot grow a second row

CHECK (config_id = 1) makes delivery_config one-row by construction. The alternative — a table with an active flag — invites two active rows and a question about which one the promise engine read.

biconditional

A finished run cannot still say running

(status = 'running') = (finished_at IS NULL) is an equality between two booleans, not an implication, so it catches both halves: a run marked succeeded with no finish time, and a run still marked running that has one.

blank guard

notes can be absent but never empty

The column is edited through NocoDB, where clicking into a text box and back out writes an empty string rather than a null. Without btrim(notes) <> '', notes IS NOT NULL would stop meaning “somebody wrote something” — the only question anyone will ask of it.

not required

A note is not forced on resolution

Requiring one on every close turns it into “ok” typed a hundred times, which is worse than an empty column: it looks like a record and is not one. The column is there for the cases that deserve it.

for link.py

Orphaned preferred links must surface here

Carried forward from 0007 and still not built: a confirmed variant with zero preferred links is a real gap, and ops.review_queue is where it has to appear, under entity_type = 'variant_link'. The table is ready to receive it; the query that finds them is Stage 7.

notes was not a new idea — the data model has specified it all along and 0009 simply omitted it. Every ops table was checked against the spec afterwards; that was the only column missing.

Judgement calls in pricing

build order

ops moved ahead of pricing to get a real FK

The build doc had pricing at 0009, which would have left variant_prices.channel_id pointing at a table that did not exist. The choice was a deferred constraint or a swap; nothing in ops depends on pricing, so the swap cost nothing.

two directions

vat_rate is pinned by the type and the CHECK

numeric(5,4) caps at 9.9999, so a bare 20 for 20% is rejected by the type. The CHECK earns its keep on what the type still allows: negatives, and the 1–10 band where a stray 5.0 would mean 500%.

asymmetric

margin_pct is bounded above but not below

Gross margin cannot reach 100% — that needs zero cost — so the ceiling is a fact about the arithmetic. There is deliberately no floor: a price below cost gives a negative margin, and that is precisely what the 15% gate exists to catch.

one constraint

Each pricing method carries its own range

ck_rules_value_matches_method is a single disjunction covering all three methods, because the legal range for value depends on which method names it. Three separate constraints would have let a row satisfy the wrong one.

    vp.channel_id,
    vp.final_price,
    cb.cost_per_base_unit,
    v.base_units_per_variant,
    round((cb.cost_per_base_unit * v.base_units_per_variant), 4) AS variant_cost,
    round((((vp.final_price - (cb.cost_per_base_unit * v.base_units_per_variant)) / NULLIF(vp.final_price, (0)::numeric)) * (100)::numeric), 3) AS gross_margin,
    vp.margin_pct AS margin_pct_at_calc,
    vp.status,
    cb.computed_at AS cost_computed_at
   FROM ((pricing.variant_prices vp
     JOIN catalog.variants v ON ((v.variant_id = vp.variant_id)))
     LEFT JOIN pricing.cost_basis cb ON ((cb.variant_id = vp.variant_id)));
