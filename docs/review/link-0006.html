The link schema, as Postgres now holds it

Two tables that join their world to ours. One is deterministic and maintained by hand; the other is fuzzy, proposed by the pipeline and confirmed by a human. They share a schema only because they both translate supplier facts into catalogue facts.

Hard rule 1, made structural

variant_links.variant_id is a foreign key to catalog.variants. There is no column here that could hold a product id, so a product-level link is not something to remember not to write — it is unrepresentable. That matters because two different operations run through this one table, and only the variant side expresses both.

multi-source matching

Two suppliers, one sellable thing

The Artis white plate and the BBP white plate are the same item from different sources, so both links point at a single variant. This is the many-to-one direction, and it is what is_preferred arbitrates.

variant grouping

One supplier, several sellable things

The white plate and the blue plate are different variants under one product. Suppliers send colour variants as separate SKUs on separate rows, so the grouping is a pipeline job — and grouping never invents combinations the supplier data does not support.

Preferred source, after 0007

Three rules, each stated as a constraint and kept true by one trigger. The constraints are the statements of fact; the trigger is what makes every human-facing action a single write instead of a careful sequence.

rule 1 · at most one

Partial unique index on the variant

UNIQUE (variant_id) WHERE is_preferred allows one preferred link per variant. “At least one” is not asserted and could not be — a variant exists before its first link does.

rule 2 · confirmed only

Preferred implies confirmed

Tightened in 0007 from the weaker “not rejected”. A proposed link can no longer be the preferred source, so Sourcing can never be pointed at a match no human has agreed to.

rule 3 · one trigger

Demote, then clear, in that stated order

link.enforce_preferred_link() runs only on a row trying to be preferred. Demote: if the row is not confirmed, drop the flag rather than raising, so rejecting or un-confirming the winner is one write. Clear: otherwise demote the variant's other links.

0006 split those two steps across two trigger functions and relied on Postgres firing BEFORE row triggers in name order — correct, but its correctness lived in the fact that one trigger name sorted before another. 0007 folded them into a single function so the order is written down. The sibling UPDATE sets is_preferred = false, which fails the trigger's own WHEN clause, so the recursive pass stops at the trigger rather than at a guard inside the function.

Confirmations sign themselves

0007 required a preferred link to be confirmed, and 0008 required a confirmed link to name its confirmer. On its own that second rule would have made the reviewer’s confirm a two-field edit — tick the status, and also supply a name — so the constraint arrives with a trigger that signs the row. Same shape as the preferred-link design: the constraint states the fact, the trigger makes the honest action a single write, and the constraint sits behind it as a backstop.

for the reviewer

One tick, no NocoDB configuration

He flips status to confirmed and link.sign_confirmation() fills in current_user and now(). Nothing to configure, and no error to learn to work around.

for the pipeline

An explicit signature is never overwritten

The trigger fires only when confirmed_by is null, so link.py writing 'pipeline' keeps it. A supplied confirmed_at is kept too — it is filled with COALESCE, not assigned outright, so a run timestamp survives.

role, not person

NocoDB signs as mos_nocodb

current_user is the connecting role, so a human edit and a machine edit stay distinguishable without a database role per person. If per-person attribution is ever wanted, have NocoDB write the logged-in user into confirmed_by and the trigger will leave it alone.

The two triggers are independent by construction, so 0008 does not reintroduce the ordering problem 0007 removed: enforce_preferred_link reads status and writes is_preferred; sign_confirmation reads status and confirmed_by and writes the two audit columns. No column is both read by one and written by the other. Tested directly: a single write that confirms and prefers in one statement produces a signed, preferred link and demotes the sibling, whichever order they fire in.

What link.py can and cannot write

What is writtenWhat happens
status = 'confirmed', both columns null Trigger signs it as the connecting role. The intended path
status = 'confirmed', confirmed_by, confirmed_at Kept verbatim; the trigger does not fire
confirmed_by alone Fails the pairing check — the signing trigger only fires when confirmed_by is null. Loud, and correct
neither, status left at its proposed default Succeeds, and the preferred-link trigger silently drops is_preferred on every single-source variant

Only the last row is quiet, and it is quiet by design — it is the same silent demotion the review queue is booked to surface.

Judgement calls

Choices the data model did not dictate. It gives the column lists and the two is_preferred mechanisms; everything below fills gaps around them.

closed at 0008

A confirmed link can no longer be signed by nobody

0007 left this open: status = 'confirmed' with both audit columns null was legal, recording a confirmation nobody made. ck_variant_links_confirmed_has_confirmer now forbids it and the signing trigger means nobody meets the error. Verified as a real backstop by disabling the trigger and watching the constraint reject the row.

known gap

The demotion is still silent

Rejecting or un-confirming the preferred link leaves the variant with no preferred source and nothing reports it. That is the cost of making it a single write. The mitigation is booked rather than built: ops.review_queue must surface any variant holding at least one confirmed link and zero preferred links, and Sourcing re-picks on its next run — an item that survives across runs means no viable candidate exists.

worth knowing

Attribution is per role, not per person

Every NocoDB confirmation signs as mos_nocodb, so the audit trail says a human confirmed it, not which human. That is the right trade for a shop where the reviewer is the reviewer, and it is the one thing to revisit if a second reviewer ever joins.

resolved at 0007

The unreachable CHECK is now reachable again

Under 0006 the demote trigger resolved the rejected-and-preferred condition before the constraint could test it, leaving a CHECK that could never fire. The 0007 constraint is stricter than the trigger's demote step in one direction — the trigger only acts on rows it is invoked for — so it earns its place rather than standing as documentation.

for the record

match_confidence is numeric(4,3), range-checked 0..1

The data model names the column but not its type or bounds. Three decimals is enough for a matching score and the range check stops a percentage being written where a fraction belongs — the classic way 0.92 becomes 92.

for the record

confirmed_by and confirmed_at must agree

Both set or both null, on each table. A confirmation with no confirmer is not a confirmation, and half-written audit columns are the kind of thing that is discovered a year later when someone asks who approved a link.

for the record

status defaults to proposed

The pipeline proposes and a human confirms, so the default is the state a row arrives in. is_preferred likewise defaults false and is NOT NULL — there is no such thing as a link whose preference is unknown. Note that this default is what makes the second failure row above silent.

for the record

category_map keys on the raw string

Not a normalised form. The raw string is what arrives on the next import, so keying on anything else would mean re-deriving the same normalisation before every lookup, and the map would quietly miss whenever the derivation changed.

for the record

category_map has no lifecycle columns

It is deterministic and hand-maintained, so there is no proposed / confirmed / rejected state to carry. An unmapped raw string is handled by not having a row here at all, and the review queue that picks it up lives in ops.

for the record

Two extra indexes

ix_variant_links_status for the review queue, which reads by state, and ix_category_map_category for "everything mapped to this node", which is what a taxonomy restructure needs. Neither is implied by a key.

CREATE FUNCTION link.enforce_preferred_link() RETURNS trigger
    LANGUAGE plpgsql
    AS $$
        BEGIN
            -- Step 1, demote. Preference is only meaningful on a link a human
            -- has confirmed, so a row arriving preferred but unconfirmed loses
            -- the flag rather than raising. Rejecting or un-confirming the
            -- current winner is therefore a single write.
            IF NEW.status <> 'confirmed' THEN
                NEW.is_preferred := false;
            END IF;

            -- Step 2, clear. At most one preferred link per variant. Skipped
            -- when the row was already preferred, so re-marking the current
            -- winner stays a no-op.
            IF NEW.is_preferred AND (TG_OP = 'INSERT' OR NOT OLD.is_preferred) THEN
                UPDATE link.variant_links
                   SET is_preferred = false
                 WHERE variant_id = NEW.variant_id
                   AND is_preferred
                   AND supplier_product_id <> NEW.supplier_product_id;
            END IF;

            RETURN NEW;
        END;
        $$;


ALTER FUNCTION link.enforce_preferred_link() OWNER TO mos_owner;

--
-- Name: sign_confirmation(); Type: FUNCTION; Schema: link; Owner: mos_owner
--

CREATE FUNCTION link.sign_confirmation() RETURNS trigger
    LANGUAGE plpgsql
    AS $$
        BEGIN
            NEW.confirmed_by := current_user;
            NEW.confirmed_at := COALESCE(NEW.confirmed_at, now());
            RETURN NEW;
        END;
        $$;
