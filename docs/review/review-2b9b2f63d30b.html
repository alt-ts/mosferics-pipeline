The review schema, and three literals that would have emptied it

Three read-only views, no tables, no data — the anti-joins a NocoDB filter view cannot express. The SQL came from a design document that had guessed at four status values it never checked. Two of those guesses would have returned too few rows and looked like an empty worklist rather than a bug.

The design document was wrong in three places

Each of these came from a CHECK constraint written months earlier contradicting prose written last week. The document had flagged its own risk — it said the status literals were the thing most likely to be wrong, and to check the migrations rather than trust it. That advice was right, and two of the three errors were exactly where it pointed.

hid the majority

IN ('approved', 'auto_approved'), not = 'approved'

0010 constrains the column to four values and says in its own comment that auto_approved and approved are both live prices; the distinction is how they got there — which is what the materiality threshold decides. At a 5% threshold most prices never queue at all and land on auto_approved, so the single literal hides the bulk of a working catalogue behind a view that merely looks quiet. Four qualifying fixture rows; the document's predicate returned two.

NULL is not false

IS DISTINCT FROM 'rejected', not <> 'rejected'

catalog.images.status is nullable free text with no CHECK and no default, unlike product_metadata.status. So <> 'rejected' evaluates to NULL for an unset status, the EXISTS finds nothing, and a product that has an image is reported as missing one. Nothing sets a status on insert, so unset is the state every image the matcher writes will arrive in — the plain <> would have been wrong for essentially every row, not an edge case.

the trap inside the trap

FOR ROLE mos_owner on the default privileges

The document's grant omitted it. Default privileges attach to the role that will create the object, defaulting to whoever runs the statement — so without the clause the statement still succeeds, pg_default_acl still gains a row, and every view a later migration adds is born invisible to NocoDB. The symptom surfaces months later and reads as a permissions problem. 0013 had already learned this; the views migration inherits the lesson rather than the bug.

Judgement calls

Choices the data model does not dictate, which is where a decision you would have made differently is cheapest to reverse — nothing has run against these views yet.

asymmetric on purpose

The image test differs between two views

missing_images is NULL-safe; ready_to_publish keeps strict = 'verified'. A worklist should not accuse a product of lacking an image it has, and a publish gate must require positive verification — NULL failing is the safe direction in one and the wrong one in the other. The asymmetry is deliberate and both views carry a comment saying so.

shipped, not deferred

Publish intent is inside the view

The document described the publish_status = 'pending' filter as something to add before showing the view to anyone. Unscoped it is every active product without an image — most of 60k rows, an inventory rather than a worklist. Left as a follow-up it is a follow-up nobody does, so it ships in the view.

no status test

The preferred-link check stands alone

0007's ck_variant_links_preferred_is_confirmed makes is_preferred imply status = 'confirmed', and its demotion trigger maintains it. Adding AND l.status = 'confirmed' would be harmless and redundant; leaving it out states that the constraint is trusted.

explicit cast

The composite key is cast, not coerced

variant_id::text || ':' || channel_id::text rather than relying on bigint || text resolving through anynonarray. NocoDB wants one unique column per relation and a composite key will not do; the cast makes the view say what it builds.

deterministic

A third sort key on the aggregate view

unmapped_categories has no natural key, so its id is a row_number(). supplier_category_raw joins the ORDER BY purely so the numbering is stable within one query when two of a supplier's categories tie on count. It is still not stable between refreshes, which is acceptable only because nothing joins to it.

symmetric teardown

The downgrade revokes before it drops

ALTER DEFAULT PRIVILEGES … REVOKE first, then each view by name, then DROP SCHEMA … CASCADE with nothing left to reach. Verified: no pg_default_acl row outlives the schema it names, and the cascade is a backstop rather than the mechanism.

open

ready_to_publish passes an undescribed product

“Everything verified” is expressed as NOT EXISTS … pending_review, which a product with zero metadata rows also satisfies. Empty is not verified. The real check is minimum-required-fields per taxonomy node and does not exist yet. Proven with a fixture, stated in the view comment, and not mistakable for that check.

open

Nothing guarantees 'verified' is the literal

catalog.images.status has no CHECK to check it against and the table is empty, so the strict test in ready_to_publish is a convention the database will not enforce. If that view is unexpectedly empty after Stage 7, this is the first thing to look at — before anything in NocoDB.

open

Two tables still sign nothing

Resolving an ops.review_queue row raises unless resolved_by and resolved_at are set with it — verified by running it. Verifying catalog.product_metadata succeeds silently with a null author, because that table has no pairing constraint at all. Only link.variant_links signs itself. The quiet one governs hard rule 3's safety fields and is the one to fix first.

Every table these views read is empty, so three views returning zero rows proves only that the SQL parses. The fixtures had to vary the deciding factor in each view, and the two rows that caught the two corrections — an image with a NULL status, a price at auto_approved — are precisely the rows a happy-path fixture does not contain. ALTER SCHEMA review OWNER TO mos_owner;

COMMENT ON SCHEMA review IS 'Read-only reporting surface for NocoDB. Every view here answers a question defined by an absence, which a NocoDB filter view cannot express because it cannot join. Connected to NocoDB as its own data source with Allow Data Edit off. Nothing writes here and nothing should join to these views.';

CREATE VIEW review.missing_images AS
 SELECT p.product_id AS id,
    p.product_id,
    p.title,
    t.path AS category_path,
    b.name AS brand,
    count(v.variant_id) AS variant_count
   FROM (((catalog.products p
     LEFT JOIN catalog.taxonomy t ON ((t.category_id = p.category_id)))
     LEFT JOIN catalog.brands b ON ((b.brand_id = p.brand_id)))
     LEFT JOIN catalog.variants v ON ((v.product_id = p.product_id)))
  WHERE ((p.status = 'active'::text) AND (NOT (EXISTS ( SELECT 1
           FROM catalog.images i
          WHERE ((i.product_id = p.product_id) AND (i.status IS DISTINCT FROM 'rejected'::text))))) AND (EXISTS ( SELECT 1
           FROM (catalog.variants v2
             JOIN ops.channel_publish cp ON ((cp.variant_id = v2.variant_id)))
          WHERE ((v2.product_id = p.product_id) AND (cp.publish_status = 'pending'::text)))))
  GROUP BY p.product_id, p.title, t.path, b.name;

ALTER VIEW review.missing_images OWNER TO mos_owner;

COMMENT ON VIEW review.missing_images IS 'Active products we are trying to publish and cannot, for want of an image. Scoped to variants with channel_publish.publish_status = pending, because image work is gated on publish intent, not ingest — unscoped this would be most of 60k rows. An image awaiting review counts as present, not missing: that is the Needs review view''s job.';

CREATE VIEW review.ready_to_publish AS
 SELECT (((cp.variant_id)::text || ':'::text) || (cp.channel_id)::text) AS id,
    cp.variant_id,
    cp.channel_id,
    v.mosferics_sku,
    p.title,
    pr.final_price,
    pr.margin_pct,
    cp.fulfilment_mode
   FROM (((ops.channel_publish cp
     JOIN catalog.variants v ON ((v.variant_id = cp.variant_id)))
     JOIN catalog.products p ON ((p.product_id = v.product_id)))
     JOIN pricing.variant_prices pr ON (((pr.variant_id = cp.variant_id) AND (pr.channel_id = cp.channel_id))))
  WHERE ((cp.publish_status <> 'published'::text) AND (p.status = 'active'::text) AND (pr.status = ANY (ARRAY['approved'::text, 'auto_approved'::text])) AND (EXISTS ( SELECT 1
           FROM link.variant_links l
          WHERE ((l.variant_id = cp.variant_id) AND l.is_preferred))) AND (EXISTS ( SELECT 1
           FROM catalog.images i
          WHERE ((i.product_id = p.product_id) AND (i.status = 'verified'::text)))) AND (NOT (EXISTS ( SELECT 1
           FROM catalog.product_metadata m
          WHERE ((m.product_id = p.product_id) AND (m.status = 'pending_review'::text))))));

ALTER VIEW review.ready_to_publish OWNER TO mos_owner;

COMMENT ON VIEW review.ready_to_publish IS 'Variant x channel rows cleared to sync: live price, preferred source, a verified image, no metadata still pending review. Keyed per channel because publish_status and price both are. NOT a minimum-required-fields check — it passes a product with zero metadata rows, which is empty rather than verified. That check does not exist yet.';

CREATE VIEW review.unmapped_categories AS
 SELECT row_number() OVER (ORDER BY (count(*)) DESC, s.name, sp.supplier_category_raw) AS id,
    sp.supplier_id,
    s.name AS supplier,
    sp.supplier_category_raw,
    count(*) AS product_count,
    min(sp.name_raw) AS example_product
   FROM ((supplier.supplier_products sp
     JOIN supplier.suppliers s ON ((s.supplier_id = sp.supplier_id)))
     LEFT JOIN link.category_map cm ON (((cm.supplier_id = sp.supplier_id) AND (cm.supplier_category_raw = sp.supplier_category_raw))))
  WHERE ((sp.supplier_category_raw IS NOT NULL) AND (cm.category_id IS NULL) AND (sp.discontinued IS NOT TRUE))
  GROUP BY sp.supplier_id, s.name, sp.supplier_category_raw;

ALTER VIEW review.unmapped_categories OWNER TO mos_owner;

COMMENT ON VIEW review.unmapped_categories IS 'Supplier categories with no link.category_map row, heaviest first so mapping effort clears the most catalogue. Pairs with an editable NocoDB grid on link.category_map: this says what is missing, that is where the mapping is added. Only covers suppliers that send a category column; BBP''s unmapped products surface in ops.review_queue instead. id is a row_number and is not stable between refreshes.';

GRANT USAGE ON SCHEMA review TO mos_nocodb;

GRANT SELECT ON TABLE review.missing_images TO mos_nocodb;

GRANT SELECT ON TABLE review.ready_to_publish TO mos_nocodb;

GRANT SELECT ON TABLE review.unmapped_categories TO mos_nocodb;

ALTER DEFAULT PRIVILEGES FOR ROLE mos_owner IN SCHEMA review GRANT SELECT ON TABLES TO mos_nocodb;

Owned by mos_owner, which can read every underlying table — so mos_nocodb holds SELECT on the views and nothing on the tables beneath them, and no INSERT or UPDATE anywhere. That is also the lever for showing margin without supplier cost, if that is ever wanted.
